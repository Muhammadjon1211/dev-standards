# Raspberry Pi Standards

We run in-restaurant systems (QR menu, ordering, kitchen/hall printing, reporting to the cloud
dashboard) on Raspberry Pi 5 and Compute Module 4 boards. One Pi per restaurant. This document is
how we set them up, deploy to them and keep them alive.

> Never write a device's password, tunnel token or IP into this repo, a README or a commit.
> Credentials live in the team's password manager; per-device notes live outside git.

---

## 1. Hardware baseline

| Item | Standard |
| --- | --- |
| Board | Raspberry Pi 5 (4–8 GB) or CM4 (≥ 2 GB) |
| Storage | ≥ 32 GB; a 6–8 GB root fills up fast — check `df -h` before every deploy |
| Network | Ethernet preferred. A link stuck at 100 Mbps usually means a bad cable |
| Power | Official supply; a brown-out shows as random hangs |
| Clock | No RTC: the clock is wrong until NTP syncs — don't trust uptimes right after boot |
| Peripherals | USB thermal printers (see [ESCPOS_PRINTERS.md](ESCPOS_PRINTERS.md)) |

## 2. OS and base software

- Raspberry Pi OS / Debian (current stable, aarch64), hostname per restaurant.
- Non-root user; `sudo` with a password on production devices.
- **SSH keys**, not passwords, for day-to-day access. Each Pi gets its **own** GitHub deploy key if
  it needs to pull private repos.
- **Tailscale** for remote access; know whether port 22 is OpenSSH or Tailscale SSH (they behave
  differently and the tailnet ACL decides).
- DHCP addresses move. Reserve an address on the router, or find the device by **MAC address** on the
  LAN — never assume an IP still belongs to the same Pi. If the SSH host key changes for a known IP,
  stop and check which device you are talking to before accepting the new key.
- Node: install from NodeSource. **Never `apt install nodejs npm`** on top of it (Debian's
  packages conflict with the NodeSource Node that pm2 uses).
- Python: `uv` installed for the service user; use its **absolute path** in units and scripts
  (non-interactive SSH has a minimal `PATH`).
- PostgreSQL from the distro, one role + database per app, password only in the app's `.env`.

## 3. Services

- Every long-running process is a **systemd unit** (Python apps, print agents, reporters, log
  shippers), or **pm2** for Node apps behind nginx.
- Units are **generated by an install script** (`deploy/install_service.sh`) that detects the user
  (`$SUDO_USER`), home, repo path and `uv` path. Never hardcode a username or `/home/<name>`.
- `Restart=always`, `EnvironmentFile=` pointing at the app's `.env`.
- **Do not set `DeviceAllow=`** in a unit that talks to a printer — it gives the service a private
  `/dev` without the udev symlinks, and the printer looks disconnected.
- Expose apps with **cloudflared** (one tunnel per app, installed as a service with its token).
  Before moving a tunnel to a Pi, uninstall the connector from wherever it ran before, or two
  connectors will serve the same hostname.
- nginx in front when several apps share the Pi; check route order and `alias` paths.

## 4. Deploy

- Build frontends **on the PC** (the Pi is slow and may have no Node toolchain). Ship `dist/`.
- Ship the backend as a `git archive` tarball of a **committed** revision (or `git pull` with the
  Pi's own deploy key). Record which commit is deployed.
- Before every deploy:
  1. Check the code on the Pi equals the last deployed commit (strip CRLF before diffing if it came
     from a Windows tree).
  2. `pg_dump` the database to `~/backups/<app>-before-<change>-<timestamp>.sql.gz`.
  3. Keep the previous build: `dist.prev` / `dist.old-<timestamp>`, `*.bak-<reason>-<timestamp>` files.
  4. Write the rollback steps down.
- Apply new migrations with `db/setup.sh --migrate-only`.
- Restart the unit, then **check the real URL and print a test ticket**.
- To try something on a live Pi without touching production, run a throwaway instance on a spare
  port with `PRINTER_ENABLED=0`, check it, then kill it.

## 5. Backups

- Daily `pg_dump` via a systemd **timer** (`Persistent=true`, small random delay), gzip, keep 14 days.
- Test a restore into a scratch database once after setting it up and compare row counts.
- Backups on the same SD card are not backups — copy them off-device (cloud bucket or the VPS).

## 6. Monitoring and the cloud

- Each Pi runs a **reporter** that pushes events, heartbeats and logs to the cloud dashboard with a
  per-device API key (`/v1/events`, `/v1/heartbeat`, `/v1/logs`).
- The admin UI on the Pi shows device problems directly (printer offline, no paper, jobs waiting).
- After a hang: check `dmesg` (USB disconnects, under-voltage), `journalctl -u <unit>`, disk space,
  `vcgencmd get_throttled`.

## 7. Making a codebase redistributable

A restaurant system is a product we install many times:

- One file to edit per install: `.env`, from a self-documenting `.env.example` (DB, admin token,
  restaurant name, currency, timezone, brand colour, printer devices, optional integrations).
- `db/setup.sh` applies the full schema on a fresh DB.
- No restaurant-specific defaults in code (name, timezone, currency, domain) — all from config.
- Refuse weak admin tokens at startup.
- `cloudflared/config.yml` and credentials are never committed; ship a `.example`.
- One default branch; a fresh `git clone` must get deployable code.
